Architectural Reference Guide

Payment Processing & Distributed Systems Concepts

Conceptual Reference vs. Local Simulation Scope
ISO 8583 & MTI / Data Elements

International standard for card-originated financial messages. Each message starts with a 4-digit Message Type Indicator (MTI) (e.g., 0100 Authorization Request, 0110 Authorization Response, 0420 Reversal Advice) followed by a binary bitmap indicating which Data Elements (DE) are present (such as DE3 Processing Code, DE4 Transaction Amount, DE11 STAN, DE39 Response Code, and DE52 PIN Data).

Idempotency vs. Visual Duplicate Check

Disabling a submit button in the UI only prevents accidental double clicks; it does not prevent network-level retries when a mobile socket times out after the server already processed the request. True backend idempotency enforces a unique constraint on Idempotency-Key in PostgreSQL, verifies the request payload hash, and atomically stores the response snapshot so retries return the original result without re-executing side effects.

Transactional Outbox Pattern

Solves the dual-write problem between a relational database and a message broker. Instead of publishing directly to RabbitMQ inside the HTTP request thread, the service inserts both the transactions row and an outbox_events row within the same local PostgreSQL ACID transaction. A background relay worker then publishes pending events asynchronously.

Delivery, Consumer Dedup & DLQ

Broker confirmation (Publisher Confirm ACK) means RabbitMQ persisted the message; consumer execution means the listener processed it; consumer ACK removes it from the queue. Because Outbox + Relay guarantees At-Least-Once delivery (not Exactly-Once), consumers must deduplicate by event_id. Messages failing repeatedly due to unrecoverable errors are routed to a Dead-Letter Queue (DLQ).

Transactional Consistency Models

Combines strong local ACID consistency for the synchronous authorization record and idempotency lock in PostgreSQL with eventual consistency for downstream settlement pre-allocation via the Outbox relay. This avoids distributed two-phase commits (2PC) across heterogeneous infrastructure while preserving auditability.

Authorization vs. Settlement

Authorization (Base I / Online) verifies cardholder funds and places a hold in milliseconds while the customer waits at the POS. Clearing & Settlement (Base II / TC50 Batch) occurs asynchronously after daily cut-off, calculating interchange/MDR fees and booking double-entry ledger payouts to merchant bank accounts.
